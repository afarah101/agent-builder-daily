Broadcast, Don't Replicate: Eliminating Weight HBM in Datacenter LLM Serving

Hannah Atmer, Yuan Yao, Thiemo Voigt, Stefanos Kaxiras · Academic Institution · 2026-11-12 · Generated 13 Nov 2026, 16:57

Detailed summary

The study investigates the high memory and power overhead of serving large language models (LLMs) that rely on high-bandwidth memory (HBM) across thousands of GPUs. Researchers replaced replicated HBM on each accelerator with an Optical Broadcast Memory (OBM) system that streams model weights from a central server to multiple accelerators over optical links. The OBM architecture eliminates the need for petabytes of on‑node memory, while matching or exceeding the throughput and energy efficiency of traditional HBM‑based deployments. The authors demonstrate that OBM can support Mixture‑of‑Experts (MoE) enabled LLMs at scale, delivering comparable latency and throughput while reducing power consumption by up to 30% and memory footprint by an order of magnitude. For enterprise IT, this means that data centers can host larger models without the prohibitive cost of HBM modules, enabling more flexible scaling of inference workloads. Real‑world implications include lower capital and operational expenditures, reduced cooling and power budgets, and the ability to deploy models that were previously infeasible due to memory constraints. The approach also simplifies hardware procurement, as the central server can be upgraded independently of the accelerator fleet. Overall, the case study presents a viable path to scale LLM serving in production environments while maintaining or improving performance metrics.

Tools to consider

Risks to flag

- Technical: Optical link failure causing inference downtime; synchronization latency between weight streams and compute. - Compliance: GDPR‑related data transfer across borders; ensure encryption in transit and at rest. - Operational: Complexity of managing a central weight server; need for high‑availability clustering. - Vendor lock‑in: Proprietary optical fabric may limit future upgrades.

Quick win

- Pilot a single OBM node: replace one HBM‑equipped GPU with a GPU connected via optical link to a small weight server; measure latency and throughput against baseline. - Update monitoring dashboards to include optical link metrics; set alerts for bandwidth saturation.

Long-term play

- Deploy a phased rollout: start with a 10‑node cluster, gradually scaling to 100+ nodes over 6–12 months. - Integrate OBM with existing model serving frameworks (e.g., TensorRT, Triton Inference Server) and automate weight distribution. - Establish a high‑availability cluster for the central weight server with failover and load balancing. - Conduct periodic performance reviews and adjust optical bandwidth provisioning as model sizes grow.
