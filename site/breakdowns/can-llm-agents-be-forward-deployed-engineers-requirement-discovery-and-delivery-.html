Can LLM Agents Be Forward-Deployed Engineers? Requirement Discovery and Delivery for Enterprise Text-to-SQL

Detailed summary

The study conducted a controlled simulation of an enterprise text‑to‑SQL engagement using large language model (LLM) agents. The goal was to evaluate whether LLM agents could autonomously discover business requirements, generate accurate SQL queries, and deliver them within the constraints of a production environment. The researchers defined a set of acceptance criteria that included requirement completeness, query correctness, execution success, and adherence to hardware and security constraints. Across 100 simulated engagements, only 25% of the runs satisfied all criteria. The remaining 75% failed due to incomplete requirement discovery, incorrect or incomplete SQL generation, execution failures on target databases, or violations of predefined hardware limits such as memory or CPU usage. The study highlighted that LLM agents often produce syntactically correct queries that do not align with the underlying schema or business logic, and that they lack robust mechanisms for validating requirements against real‑world data. For enterprise IT, these findings are significant because many organizations are exploring LLM‑driven automation to accelerate data analytics, reduce developer toil, and lower operational costs. The research demonstrates that without rigorous validation and governance, deploying LLM agents in production can lead to incorrect data retrieval, security gaps, and wasted compute resources. The real‑world implications include the need for tighter integration between LLMs and data cataloging tools, the implementation of automated test harnesses that validate generated queries against a sandbox, and the establishment of clear ownership for requirement specification. Cloud infrastructure managers must recognize that relying on automated code generation without sufficient oversight introduces risks that can affect compliance, performance, and cost predictability. The study therefore serves as a cautionary benchmark, urging enterprises to adopt a phased, risk‑aware approach before fully integrating LLM agents into their data pipelines.

Tools to consider

- OpenAI GPT‑4o or Azure OpenAI Service for LLM inference. - Snowflake or AWS Redshift for data warehousing with built‑in query validation. - dbt (data build tool) for schema tests and lineage tracking. - DataRobot or Dataiku for automated data profiling and requirement extraction. - Terraform or Pulumi for IaC to provision isolated sandbox environments for query testing.

Risks to flag

- Technical: Incorrect query logic leading to data corruption or loss. - Compliance: UK GDPR – ensure LLM does not expose personal data in training or inference. - Operational: Uncontrolled compute costs due to runaway LLM inference. - Governance: Lack of audit trails for generated queries and their approvals.

Quick win

Deploy an LLM‑powered query assistant in a single, low‑risk data domain (e.g., marketing analytics) with a sandbox environment. Set up automated unit tests that compare generated SQL against a known correct baseline. Measure accuracy after 30 days and report findings to stakeholders.

Long-term play

Over 6–12 months, roll out a governance framework that includes: - Requirement specification templates integrated with Jira or ServiceNow. - Continuous integration pipelines that run generated queries against a test cluster before promotion. - A monitoring dashboard that tracks query performance, cost, and compliance violations. - Periodic audits of LLM outputs and retraining cycles to improve accuracy.
